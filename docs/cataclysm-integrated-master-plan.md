# Gitagotchi 대격변 통합기획서

## Page 01. 통합기획서 목적

이 문서는 기존 네 개의 대격변 기획서를 하나의 실행 가능한 통합기획서로 합친 문서입니다. 대상 문서는 다음 네 가지입니다.

- `docs/cataclysm-update-plan.md`
- `docs/cataclysm-ui-ux-plan.md`
- `docs/cataclysm-game-system-plan.md`
- `docs/cataclysm-pet-evolution-system-plan.md`

이 통합기획서는 단순 요약 문서가 아닙니다. 제품 방향, UI/UX 구조, 게임 시스템, 펫·진화 시스템, 코드 리팩터링 방향, 검증 기준을 하나로 묶어 실제 앱 구조 변경의 기준으로 사용하기 위한 문서입니다.

이번 리팩터링의 핵심 제약은 명확합니다.

> VS Code에 저장되는 사용자 데이터 구조는 보존하고, 그 외 내부 앱 구조는 대격변 기획에 맞게 재구성합니다.

보존해야 할 것은 사용자의 기존 Gitagotchi 상태입니다. 바꿔야 할 것은 기능이 흩어져 있는 내부 구조, UI와 도메인 규칙의 결합, 엔드게임 시스템 확장성 부족, 대격변 기능을 장기적으로 운영하기 어려운 모듈 경계입니다.

## Page 02. 제품 한 줄 정의

Gitagotchi는 개발자의 작업 루틴을 방해하지 않고, VS Code 안에서 개발 행동을 펫 성장, 오늘의 퀘스트, 레이드, 시즌, 연구소, 환생, 장기 기록으로 변환하는 개발자용 성장 RPG 확장입니다.

제품의 핵심은 "게임을 따로 플레이하는 것"이 아닙니다. 사용자는 원래 하던 개발을 계속합니다. Gitagotchi는 그 행동을 해석해 성장 세계로 번역합니다.

제품이 답해야 하는 질문은 다음과 같습니다.

- 오늘 무엇을 하면 되는가?
- 방금 한 개발 행동이 어떤 성취가 되었는가?
- 내 펫은 어떤 개발 스타일로 성장하고 있는가?
- 고레벨 이후에도 남는 목표는 무엇인가?
- 오래 사용한 흔적은 어디에 남는가?
- 다음 접속 때 무엇을 기대할 수 있는가?

## Page 03. 현재 문제 정의

기존 Gitagotchi는 펫 성장이라는 강한 감정적 출발점을 가지고 있습니다. 하지만 단순 성장 표시만으로는 반복 사용을 오래 유지하기 어렵습니다. 초반에는 귀엽고 신선하지만, 고레벨 사용자는 곧 다음 목표를 잃습니다.

핵심 문제는 다음과 같습니다.

- 일일 목표가 약합니다.
- 성장 이후의 엔드게임이 부족합니다.
- 개발 스타일이 펫 정체성으로 충분히 연결되지 않습니다.
- 성취 순간이 화면에서 크게 느껴지지 않습니다.
- 레벨업 이후에도 남는 영구 기록이 부족합니다.
- 코드 구조가 대격변 시스템을 장기적으로 확장하기에 충분히 분리되어 있지 않습니다.

이 문제는 기능을 몇 개 더 붙이는 방식으로 해결되지 않습니다. 제품 동기 구조와 코드 구조를 함께 바꿔야 합니다.

## Page 04. 대격변 목표

이번 대격변의 목표는 Gitagotchi를 다음 구조로 바꾸는 것입니다.

- 매일 열 이유가 있는 앱
- 개발 행동이 즉시 보상으로 바뀌는 앱
- 고레벨 사용자가 레이드와 환생을 반복할 이유가 있는 앱
- 펫 외형과 정체성이 개발 스타일을 반영하는 앱
- 시즌과 회고로 장기 기록이 남는 앱
- 내부 구조가 기능별로 분리되어 확장 가능한 앱

대격변 완료 상태는 다음 문장으로 판단합니다.

> 사용자는 패널을 열고 5초 안에 오늘의 목표, 현재 펫 상태, 진행 중인 레이드, 최신 성취, 장기 성장 흔적을 이해할 수 있어야 합니다.

## Page 05. 보존해야 할 VS Code 데이터 구조

이번 리팩터링에서 가장 중요한 보존 경계는 `PetState`와 저장 어댑터가 다루는 영속 데이터입니다. 사용자의 기존 저장 데이터는 프로덕션 자산입니다. 내부 구현을 바꾸더라도 저장 구조를 임의로 깨면 안 됩니다.

보존 대상:

- `PetState`
- `DailyQuestState`
- `EndgameState`
- `RaidState`
- `SeasonState`
- `WeeklyReviewState`
- `PetLogEntry`
- `GrowthBreakdownEntry`
- 저장 스키마 버전과 마이그레이션 흐름
- 기존 VS Code globalState 저장 키

허용되는 변경:

- 내부 계산 모듈 분리
- UI 렌더링 helper 분리
- 도메인 feature 디렉터리 신설
- 명령 처리 계층 분리
- 문서와 테스트 추가

금지되는 변경:

- 기존 사용자 저장 데이터를 삭제하는 변경
- 스키마 버전 없이 필수 필드를 바꾸는 변경
- 기존 저장 키를 임의 변경하는 변경
- 임시 마이그레이션 우회 코드

## Page 06. 사용자 세그먼트

Gitagotchi는 세 사용자군을 동시에 만족해야 합니다.

신규 사용자:

- 앱을 처음 열고 펫과 오늘의 퀘스트를 봅니다.
- 복잡한 엔드게임보다 즉시 반응을 원합니다.
- 첫날에 작은 보상을 경험해야 합니다.

반복 사용자:

- 매일 퀘스트와 시즌 진행을 확인합니다.
- 콤보와 장식을 통해 누적 재미를 느낍니다.
- 짧은 확인만으로도 앱을 계속 사용할 이유가 있어야 합니다.

고레벨 사용자:

- 레이드 보스, 직업 빌드, 연구소, 환생, 별을 목표로 삼습니다.
- 장식과 격파 기록을 수집합니다.
- 초기화 이후에도 남는 영구 성취를 원합니다.

## Page 07. 핵심 제품 루프

대격변 이후 Gitagotchi의 핵심 루프는 다음과 같습니다.

1. 사용자가 VS Code에서 개발합니다.
2. diff, commit, diagnostics, idleTick 이벤트가 생성됩니다.
3. 성장 엔진이 경험치, 상태 변화, 스타일 점수를 계산합니다.
4. 오늘의 퀘스트가 진행됩니다.
5. 엔드게임 엔진이 직업 보너스, 콤보, 레이드, 시즌, 회고를 계산합니다.
6. 레벨과 진화가 갱신됩니다.
7. 펫 정체성, 종족, 스킬이 갱신됩니다.
8. 로그와 최신 성취 배너가 생성됩니다.
9. 사용자는 패널에서 결과를 확인하고 다음 목표를 이해합니다.

이 루프는 자동이어야 합니다. 사용자가 게임을 진행하기 위해 별도 반복 클릭을 강요받으면 안 됩니다.

## Page 08. UI/UX 통합 방향

UI는 게임처럼 보이되, 개발 도구의 밀도를 유지해야 합니다. Gitagotchi는 VS Code 안에서 작동하므로 지나치게 화려한 랜딩 페이지나 설명형 화면이 아니라, 스캔 가능한 상태판이어야 합니다.

화면 우선순위:

1. 최신 성취 배너
2. 언어와 보조 액션
3. 펫 카드
4. 런타임 프로필
5. 상태 카드
6. 스타일 점수
7. 오늘의 퀘스트
8. 엔드게임 보드
9. 액션 독
10. 도움말 모달

핵심 UX 기준:

- 설명보다 현재 상태를 먼저 보여줍니다.
- 숫자와 진행 바를 함께 제공합니다.
- 성취 순간은 로그보다 먼저 보여줍니다.
- 고레벨 정보는 숨기지 않고 압축합니다.
- 위험 액션은 실수 방지 절차가 필요합니다.

## Page 09. 펫 카드 기획

펫 카드는 Gitagotchi의 감정적 중심입니다. 이 영역은 앱을 단순 생산성 도구가 아니라 펫 성장 경험으로 느끼게 만듭니다.

펫 카드 구성:

- 계열 라벨
- 레벨 배지
- 스프라이트 스테이지
- 오늘 만져주기 하트
- 환생 별 궤도
- 이름
- 호출명
- 단계와 전문성
- 장식 칩
- 카드 경험치 바

펫 카드는 사용자가 "내 Gitagotchi"라고 느끼는 곳입니다. 따라서 이름, 외형, 장식, 별이 명확히 보여야 합니다. 다만 장식과 별은 펫을 가리면 안 됩니다.

## Page 10. 시스템 카드 기획

시스템 카드는 기능적 상태판입니다. 사용자는 이 영역에서 현재 수치와 다음 행동을 이해합니다.

시스템 카드 구성:

- 레벨과 경험치
- 기분, 포만감, 에너지, 건강
- 상태, 단계, 계열, 전문성
- 스타일 점수
- 오늘의 퀘스트
- 엔드게임 보드
- 액션 독

설계 원칙:

- 모든 상태는 숫자와 시각적 미터를 함께 사용합니다.
- 포만감은 배고픔의 반대값으로 표시합니다.
- 스타일 점수는 개발자의 자기 이해를 돕습니다.
- 퀘스트와 엔드게임은 같은 화면에서 이어져야 합니다.

## Page 11. 오늘의 퀘스트 기획

오늘의 퀘스트는 매일 앱을 열 이유를 만듭니다.

퀘스트 목록:

- 버그 사냥
- 정리의 날
- 현장 가이드
- 출하 준비
- 균형 훈련

퀘스트 상태:

- 미선택
- 진행 중
- 완료

퀘스트 설계 원칙:

- 하루에 3개 후보를 제공합니다.
- 사용자는 하나를 선택합니다.
- 진행 중에는 변경하지 않습니다.
- 완료 보상은 하루 1회입니다.
- 보상은 경험치, 기분, 장식입니다.

퀘스트는 단기 목표이면서 수집 시스템의 입구입니다.

## Page 12. 장식과 수집 기획

장식은 사용자의 행동 기록을 수집 가능한 형태로 바꿉니다.

장식 분류:

- 퀘스트 장식
- 레이드 장식
- 시즌 장식
- 연구소 장식

장식 UX:

- 장식은 칩으로 표시합니다.
- 장식이 없으면 빈 상태 문구를 표시합니다.
- 중복 지급은 피합니다.
- 향후 도감과 컬렉션 화면으로 확장합니다.

장식은 경험치보다 오래 기억되는 보상입니다. 사용자는 "나는 레거시 드래곤을 잡았다"를 장식으로 확인할 수 있어야 합니다.

## Page 13. 직업 빌드 기획

직업 빌드는 고레벨 사용자의 자기 표현과 최적화 시스템입니다.

직업 목록:

- 릴리즈 마스터
- 코드 가드너
- 버그 트래커
- 아카이비스트
- 밸런스 아키텍트

직업 보너스:

- 선호 스타일이 성장하면 추가 경험치와 기분 보상
- 별 수가 많을수록 보너스 증가

기획 의도:

- 사용자가 자신의 개발 스타일을 선언합니다.
- 환생 별이 빌드 효율로 연결됩니다.
- 향후 레이드 상성과 직업 전용 퀘스트로 확장합니다.

## Page 14. 콤보 기획

콤보는 좋은 개발 흐름을 발견하는 시스템입니다.

현재 콤보:

- 스태빌라이저: 테스트 변경, 문제 해결, 커밋
- 정리 완료: 정리 diff, 문서 변경, 커밋
- 스펙 주도: 문서 변경, 코드 변경, 커밋

콤보 보상:

- 최초 발견 시 경험치 45
- 기분 5

콤보는 사용자의 반복 행동을 단순 누적이 아니라 의미 있는 작업 순서로 해석합니다. 무한 파밍을 막기 위해 최초 발견 중심으로 운영합니다.

## Page 15. 레이드 보스 기획

레이드는 고레벨 사용자의 핵심 공략 콘텐츠입니다.

보스 목록:

- 레거시 드래곤
- 버그 로드
- 릴리즈 골렘
- 의존성 망령

각 보스는 개발자의 실제 어려움을 상징합니다. 레거시 드래곤은 기술 부채, 버그 로드는 오류와 회귀, 릴리즈 골렘은 배포와 마감, 의존성 망령은 패키지와 환경 문제를 뜻합니다.

레이드 UI:

- 보스 실루엣
- 보스 이름
- HP 숫자
- 체력바
- 격파 기록

레이드 보상:

- 타격 경험치
- 클리어 경험치
- 기분 보상
- 보스별 장식

## Page 16. 시즌 기획

시즌은 반복 사용의 달력입니다. 매일의 작은 행동이 시즌 진행률로 누적됩니다.

현재 시즌:

- breakpointRuins
- 목표 진행률 500
- 보상: 시즌 유물

시즌 설계 원칙:

- 거의 모든 긍정적 개발 행동이 시즌에 기여합니다.
- milestone 보상은 중복 지급하지 않습니다.
- 향후 시즌별 보스, 장식, 칭호로 확장합니다.

시즌은 사용자가 다음 달에도 앱을 열 이유를 만드는 운영 단위입니다.

## Page 17. 연구소와 별 조각 기획

연구소는 경험치를 장기 자원으로 전환하는 시스템입니다.

현재 별 조각 제작:

- EXP 250 이상 필요
- 이미 별 조각이 있으면 중복 제작하지 않음
- 제작 시 EXP 250 소모
- labExpSpent 증가
- 별 조각 장식 지급

기획 의도:

- 즉시 레벨업과 장기 준비 사이의 선택을 만듭니다.
- 환생과 별 투자 트리의 기반이 됩니다.
- 고레벨 사용자에게 자원 관리 목표를 제공합니다.

## Page 18. 마스터리와 주간 회고 기획

마스터리는 사용자의 전체 여정을 압축하는 지표입니다. 현재 레벨이 현재 생애의 성장이라면, 마스터리는 여러 생애를 관통하는 누적 성장입니다.

주간 회고는 사용자의 개발 성향을 서사적으로 요약합니다.

회고 유형:

- 출하 중심의 주
- 리팩터 중심의 주
- 디버그 중심의 주
- 지식 축적의 주
- 지속성의 주

회고는 평가가 아니라 기록이어야 합니다. 사용자를 판단하지 않고, 이번 주 어떤 개발 스타일이 강했는지 보여줍니다.

## Page 19. 환생과 별 기획

환생은 장기 루프의 핵심입니다.

조건:

- 레벨 30 이상
- ultimate 단계
- alive 상태

보상:

- 기본 별 1개
- 30레벨 초과 20레벨마다 추가 별 1개

환생 후:

- 레벨과 경험치는 초기화
- 상태는 안정적으로 회복
- 계열과 전문성은 초기화
- 스타일 점수 일부 보존
- 별과 환생 횟수 보존

환생은 초기화가 아니라 깊어진 시작이어야 합니다.

## Page 20. 펫·진화 시스템 기획

펫은 사용자의 개발 습관이 반영되는 디지털 동료입니다.

진화 단계:

- egg
- junior
- mid
- senior
- architect

표시 단계:

- 알
- 유년기
- 성장기
- 전문가
- 궁극

진화는 단순 레벨 체크가 아니라 케어 상태와 스타일 균형을 함께 봅니다. 특히 궁극 단계는 모든 스타일 점수와 케어 상태를 요구합니다.

## Page 21. 계열·전문성·종족 기획

계열:

전문성:

## Page 22. 스킬과 무드 기획

스킬:

- commitRoar

무드:

스킬은 특정 성장 방향이 실제 보너스로 이어지는 증거입니다. 무드는 펫 상태를 감정적으로 보여주는 표현입니다.

스킬과 무드는 펫이 단순 이미지가 아니라 상태를 가진 존재처럼 느껴지게 만듭니다.

## Page 23. 로그와 성취 피드백 기획

로그는 보상의 증거이고, 최신 성취 배너는 감정적 피드백입니다.

breakdown 예:

- quest.bugHunt
- combo.stabilizer
- raid.damage.releaseGolem
- raid.defeat.releaseGolem
- reincarnation

피드백 원칙:

- 사용자는 왜 보상을 받았는지 알아야 합니다.
- 최신 이벤트는 배너로 먼저 보입니다.
- 상세 근거는 로그에서 확인합니다.
- 문구는 과장보다 명확성을 우선합니다.

## Page 24. 리팩터링 비전

현재 앱은 기능이 늘어나면서 `core`, `ui`, `extension`에 책임이 섞이고 있습니다. 대격변 이후에는 기능별 도메인 경계를 강화해야 합니다.

리팩터링 목표:

- VS Code 어댑터와 도메인 규칙 분리
- 게임 시스템 도메인 모듈화
- 펫·진화 시스템 도메인 모듈화
- UI 프레젠테이션 helper 분리
- 명령 처리 흐름 명확화
- 테스트 가능한 순수 함수 경계 확대

보존 원칙:

- 저장 데이터 타입은 유지합니다.
- 외부 명령 동작은 유지합니다.
- 기존 테스트는 계속 통과해야 합니다.

## Page 25. 목표 아키텍처

목표 구조는 다음과 같습니다.

```text
src/
  extension.ts
  adapters/
  core/
    petState.ts
    events.ts
    rules/
  domain/
    game/
    pet/
  application/
    petLifecycleService.ts
    petCommandService.ts
  ui/
    components/
    petPanelPresentation.ts
```

이번 단계에서 모든 파일을 무리하게 이동할 필요는 없습니다. 우선 도메인 feature entrypoint를 만들고, 기존 core 구현을 안정적으로 감싸는 구조부터 적용합니다.

## Page 26. 리팩터링 1단계

1단계는 저장 데이터 구조를 건드리지 않고 내부 도메인 경계를 세우는 작업입니다.

작업:

- `src/domain/game` 생성
- 게임 시스템 공개 API를 `gameSystem.ts`로 집약
- 퀘스트와 엔드게임 엔진을 game domain에서 재노출
- `growthEngine.ts`가 세부 파일 대신 domain entrypoint를 참조
- 테스트는 기존 동작을 유지

효과:

- 게임 시스템의 공개 표면이 명확해집니다.
- 향후 레이드, 시즌, 연구소 확장이 쉬워집니다.
- 기존 저장 데이터 구조는 그대로 유지됩니다.

## Page 27. 리팩터링 2단계

2단계는 펫·진화 시스템 경계를 세우는 작업입니다.

작업:

- `src/domain/pet` 생성
- 진화, 정체성, 무드, 생명 상태 관련 공개 API를 `petSystem.ts`로 집약
- UI와 성장 엔진이 직접 세부 구현을 많이 알지 않게 정리
- 스프라이트 선택은 UI/character 경계에 남기되 펫 정체성 계산은 domain/pet으로 모읍니다.

효과:

- 펫 정체성과 게임 진행 계산이 분리됩니다.
- 진화 조건 변경이 쉬워집니다.
- 도감과 스프라이트 확장이 쉬워집니다.

## Page 28. 리팩터링 3단계

3단계는 UI 프레젠테이션을 구성 요소 단위로 분리하는 작업입니다.

작업:

- moment banner helper 분리
- quest board helper 분리
- endgame board helper 분리
- pet card helper 분리
- 상태 표시 helper 분리

주의:

- 이번 단계에서 HTML 결과가 바뀌면 테스트를 함께 갱신합니다.
- UI 분리는 동작 변경이 아니라 유지보수성 개선이어야 합니다.

효과:

- 펫 패널 파일 크기가 줄어듭니다.
- UI 상태별 테스트가 쉬워집니다.
- 향후 화면 개편이 안전해집니다.

## Page 30. 완료 정의

이번 통합 작업은 다음 조건을 만족해야 완료로 판단합니다.

- 30장 분량의 통합기획서가 작성되어 있습니다.
- 통합기획서가 기존 4개 기획서의 내용을 연결합니다.
- 앱 구조가 기획서의 목표 아키텍처 방향으로 리팩터링됩니다.
- VS Code 저장 데이터 구조는 보존됩니다.
- 기존 테스트가 모두 통과합니다.
- 깨진 한글이 없습니다.
- 문서와 코드 변경 범위가 요청과 직접 관련되어 있습니다.
- 리팩터링이 임시 우회가 아니라 장기 구조 개선입니다.

최종 제품 판단:

Gitagotchi는 이제 단순 펫 성장 확장이 아니라, 개발자의 반복 루틴을 장기 성장 RPG로 바꾸는 VS Code 확장입니다. 이번 통합기획서와 리팩터링은 그 방향을 문서와 코드 구조 양쪽에서 고정하기 위한 기준입니다.
