# Gitagotchi 대격변 업데이트 UI/UX 상세 기획서

## 0. 문서 목적

이 문서는 `Gitagotchi 대격변 업데이트 제품 기획서`를 실제 화면 경험으로 옮기기 위한 UI/UX 상세 기획서입니다. 제품 기획서가 "왜 이 업데이트가 필요한가"와 "어떤 시스템이 들어가는가"를 정의했다면, 이 문서는 사용자가 VS Code 안에서 무엇을 보고, 어떤 순서로 이해하고, 어떤 순간에 재미를 느끼며, 어떤 상태에서 어떤 행동을 할 수 있어야 하는지를 정의합니다.

이번 UI/UX 기획의 대상은 Gitagotchi의 핵심 패널입니다. 패널은 단순 정보판이 아니라 다음 역할을 동시에 수행해야 합니다.

- 펫을 감정적으로 확인하는 공간
- 오늘의 목표를 고르는 공간
- 레이드와 시즌을 추적하는 엔드게임 대시보드
- 성취 순간을 즉시 보여주는 피드백 표면
- 고레벨 사용자의 장기 기록을 보여주는 수집 화면
- VS Code 업무 흐름을 방해하지 않는 짧은 확인 도구

## 1. UX 비전

Gitagotchi의 UI는 "개발자용 작은 성장 세계"처럼 느껴져야 합니다. 하지만 VS Code 확장이므로 과하게 게임 화면처럼 행동해서는 안 됩니다. 사용자는 코드를 작성하러 VS Code를 열었지, 별도 게임을 하러 온 것이 아닙니다. 따라서 UI는 조용하고 빠르게 스캔 가능해야 하며, 성취 순간만 짧고 강하게 빛나야 합니다.

핵심 UX 문장은 다음과 같습니다.

> 사용자는 패널을 열고 5초 안에 오늘의 목표, 현재 펫 상태, 진행 중인 레이드, 방금 얻은 성취를 이해해야 합니다.

이 문장을 만족하려면 화면은 복잡한 설명보다 상태, 진행률, 보상, 다음 행동을 우선해야 합니다.

## 2. 디자인 원칙

### 2.1 첫 화면은 설명서가 아니라 상태판이어야 합니다

사용자가 패널을 열었을 때 가장 먼저 봐야 하는 것은 기능 설명이 아닙니다. 최신 성취, 펫, 레벨, 퀘스트, 레이드 상태입니다. 도움말은 필요할 때 열 수 있어야 하지만 기본 화면을 차지하면 안 됩니다.

### 2.2 게임성은 표면에, 복잡성은 구조 안에 둡니다

퀘스트, 레이드, 시즌, 환생은 복잡한 시스템입니다. 하지만 화면은 복잡한 규칙을 길게 설명하지 않고, 현재 상태와 다음 행동만 보여줘야 합니다. 예를 들어 레이드는 "보스 이름", "보스 실루엣", "HP", "시작 버튼"만으로 첫 이해가 가능해야 합니다.

### 2.3 개발 도구의 밀도를 유지합니다

VS Code 내부 UI이므로 카드, 버튼, 텍스트 크기는 과장되면 안 됩니다. 화면은 운영 도구처럼 조밀하고 스캔 가능해야 합니다. 다만 펫 영역과 순간 배너에는 감정적 표현을 허용합니다.

### 2.4 고레벨 정보는 숨기지 말고 압축합니다

고레벨 사용자는 레이드, 시즌, 마스터리, 환생, 연구소 정보를 자주 확인합니다. 이 정보를 별도 깊은 화면에 숨기면 반복 사용성이 떨어집니다. 따라서 핵심 숫자는 한 화면에 보이되, 각 시스템의 자세한 설명은 보조 텍스트와 상태값으로 압축합니다.

### 2.5 성취 순간은 화면 최상단에서 처리합니다

사용자가 방금 한 행동의 결과는 로그 아래에 묻히면 안 됩니다. 최신 성취는 패널 최상단 배너로 보여주고, 사용자가 "내 행동이 방금 의미 있는 결과를 만들었다"는 것을 즉시 느끼게 해야 합니다.

## 3. 정보 구조

패널의 정보 우선순위는 다음과 같습니다.

1. 최신 성취 배너
2. 언어와 보조 액션
3. 펫 카드
4. 런타임 프로필과 핵심 상태
5. 스타일 점수
6. 오늘의 퀘스트
7. 엔드게임 보드
8. 주요 액션 버튼
9. 도움말 모달

이 순서는 신규 사용자와 고레벨 사용자의 요구를 동시에 만족시키기 위한 구조입니다. 신규 사용자는 펫 카드와 퀘스트를 중심으로 이해하고, 고레벨 사용자는 엔드게임 보드와 순간 배너를 중심으로 목표를 확인합니다.

## 4. 전체 레이아웃

### 4.1 데스크톱 기본 구조

기본 패널은 최대 폭을 제한한 `page-shell` 안에 구성합니다. 넓은 화면에서는 두 열 구조를 사용합니다.

- 왼쪽: 몬스터 카드
- 오른쪽: 시스템 카드

왼쪽 몬스터 카드는 감정적 중심입니다. 오른쪽 시스템 카드는 실질적인 상태와 행동의 중심입니다.

권장 구조:

```text
최신 성취 배너
언어 선택 / 이름 변경 / 초기화 / 도움말
┌───────────────┬──────────────────────────┐
│ 펫 카드        │ 시스템 카드                │
│ 스프라이트     │ 레벨, 상태, 스타일         │
│ 이름, 장식     │ 퀘스트, 엔드게임, 액션     │
└───────────────┴──────────────────────────┘
푸터
```

### 4.2 좁은 화면 구조

좁은 화면에서는 단일 열로 쌓습니다.

순서:

1. 최신 성취 배너
2. 언어와 보조 액션
3. 몬스터 카드
4. 시스템 카드
5. 액션 버튼

좁은 화면에서도 펫이 먼저 보여야 합니다. Gitagotchi의 정체성은 펫이며, 숫자 대시보드가 먼저 나오면 제품의 감정적 차별점이 약해집니다.

### 4.3 스크롤 정책

패널은 세로 스크롤을 허용합니다. 단, 첫 화면에서 최소한 다음 요소가 보여야 합니다.

- 최신 성취 배너가 있는 경우 배너 전체
- 언어/도움말 액션
- 펫 카드 상단과 스프라이트
- 시스템 카드의 레벨/경험치 일부

엔드게임 보드는 첫 화면 아래에 위치해도 되지만, 고레벨 사용자가 너무 깊게 스크롤하지 않도록 시스템 카드 내부에서 퀘스트 바로 아래에 둡니다.

## 5. 최신 성취 배너

### 5.1 역할

최신 성취 배너는 사용자가 방금 한 개발 행동의 의미를 해석하는 가장 중요한 피드백 장치입니다. 이 배너는 Gitagotchi가 단순히 수치를 업데이트하는 앱이 아니라, 사용자의 활동을 사건으로 바꾸는 앱이라는 느낌을 줍니다.

### 5.2 표시 조건

배너는 최신 로그를 기반으로 표시합니다. 표시 우선순위는 다음과 같습니다.

1. 레이드 클리어
2. 레이드 타격
3. 콤보 발생
4. 퀘스트 완료
5. 환생
6. 일반 성장

동시에 여러 이벤트가 발생하는 경우, 사용자에게 가장 희귀하고 의미 있는 이벤트를 우선합니다.

### 5.3 콘텐츠 구조

배너는 다음 요소로 구성합니다.

- 시각 플래시
- 성취 제목
- 짧은 결과 설명

예시:

```text
레이드 클리어
보스를 격파했습니다. +120 EXP와 희귀 전리품을 얻었습니다.
```

### 5.4 톤

문구는 과도하게 들뜨면 안 됩니다. 개발 도구 안에서 자연스럽게 읽혀야 합니다. "대단해요!" 같은 일반적 칭찬보다 무엇이 일어났는지를 명확히 말합니다.

좋은 예:

- 오늘의 집중 목표를 완료했습니다.
- 작업이 보스에게 피해를 줬습니다.
- Gitagotchi가 다음 생으로 별을 가져갑니다.

피해야 할 예:

- 완전 미쳤습니다.
- 당신은 최고입니다.
- 지금 당장 더 플레이하세요.

### 5.5 시각 상태

배너 종류별 시각 톤:

- 일반 성장: 낮은 강조, 부드러운 색
- 퀘스트 완료: 중간 강조, 보상 느낌
- 콤보: 리듬감, 짧은 펄스
- 레이드 타격: 긴장감, 강한 대비
- 레이드 클리어: 가장 강한 강조
- 환생: 차분하지만 특별한 광원

### 5.6 접근성

배너는 애니메이션 없이도 의미가 전달되어야 합니다. 제목과 설명 텍스트만으로 이벤트 종류를 이해할 수 있어야 합니다. 애니메이션은 보조 효과입니다.

## 6. 상단 유틸리티 바

### 6.1 구성

상단 유틸리티 바는 다음 요소를 포함합니다.

- 언어 선택
- 이름 변경
- 초기화
- 도움말

### 6.2 언어 선택

언어 선택은 짧은 코드 버튼으로 유지합니다.

- EN
- KO
- JA
- ZH

선택된 언어는 active 상태로 표시합니다. 버튼은 기능 버튼처럼 보이되, 화면의 주인공이 되어서는 안 됩니다.

### 6.3 이름 변경

이름 변경은 낮은 우선순위의 보조 액션입니다. 펫에게 애착을 주는 기능이므로 존재해야 하지만, 매일 누르는 버튼은 아닙니다.

### 6.4 초기화

초기화는 위험 액션입니다. 색상이나 라벨에서 위험성을 드러내야 하며, 실제 실행 전 확인 절차가 필요합니다. UI 문구는 명확해야 합니다.

권장 문구:

- 버튼: 초기화
- 확인 제목: Gitagotchi를 초기화할까요?
- 설명: 현재 이름, 레벨, 상태, 스킬, 로그가 삭제됩니다.

### 6.5 도움말

도움말은 `?` 버튼으로 충분합니다. 버튼은 작아야 하지만 클릭 영역은 최소 28px 이상을 유지합니다. 도움말은 기본 화면을 침범하지 않고 모달로 열립니다.

## 7. 펫 카드

### 7.1 역할

펫 카드는 Gitagotchi의 감정적 중심입니다. 사용자는 이 카드에서 자신의 펫을 확인하고, 이름과 레벨, 진화 단계, 장식, 별을 봅니다. 이 영역은 앱의 "캐릭터성"을 담당합니다.

### 7.2 구성 요소

펫 카드는 다음 요소로 구성합니다.

- 계열 라벨
- 레벨 배지
- 스프라이트 스테이지
- 오늘 만져주기 하트
- 환생 별 궤도
- 이름
- 호출명
- 단계와 전문성 칩
- 장식 칩
- 카드 경험치 바

### 7.3 스프라이트 스테이지

스프라이트 스테이지는 카드에서 가장 눈에 띄는 영역입니다. 펫 스프라이트는 중앙에 배치하고, 별 궤도와 하트 같은 보조 요소는 펫을 가리지 않아야 합니다.

규칙:

- 펫은 항상 카드의 중심에 있어야 합니다.
- 별 궤도는 환생 별이 있을 때만 표시합니다.
- 하트는 오늘 만져준 상태를 표시합니다.
- 장식은 스프라이트를 가리지 않고 하단 칩으로 표시합니다.

### 7.4 이름 영역

이름은 사용자의 애착을 만드는 핵심 텍스트입니다. 너무 작으면 감정적 의미가 약해지고, 너무 크면 도구 UI와 충돌합니다.

규칙:

- 이름은 줄바꿈을 허용합니다.
- 긴 이름은 영역 밖으로 넘치지 않아야 합니다.
- 호출명은 보조 텍스트로 처리합니다.
- 레벨 정보는 중복되더라도 펫 카드와 시스템 카드 양쪽에 있어도 됩니다. 하나는 감정적 레벨, 하나는 상태판 레벨입니다.

### 7.5 장식 칩

장식은 오늘의 퀘스트와 레이드 보상으로 얻는 수집 요소입니다. 장식은 단순 목록이 아니라 사용자의 흔적입니다.

상태:

- 장식 없음: "아직 퀘스트 전리품 없음"
- 장식 있음: 장식 이름 칩 목록

규칙:

- 칩은 줄바꿈을 허용합니다.
- 너무 많은 장식은 향후 컬렉션 화면으로 분리할 수 있습니다.
- 현재 패널에서는 최근 또는 핵심 장식만 보여주는 확장안을 고려할 수 있습니다.

### 7.6 환생 별 궤도

별 궤도는 고레벨 사용자의 장기 성취를 시각화합니다. 별은 단순 숫자보다 더 강한 의미를 줘야 합니다.

규칙:

- 별이 0개면 표시하지 않습니다.
- 별이 1개 이상이면 스프라이트 주변에 배치합니다.
- 최대 7개까지 직접 표시하고, 그 이상은 숫자 보조 표기를 고려합니다.
- 별은 펫보다 더 주목받으면 안 됩니다.

## 8. 시스템 카드

### 8.1 역할

시스템 카드는 Gitagotchi의 조작과 상태 확인 중심입니다. 사용자는 이 영역에서 레벨, 경험치, 상태, 스타일, 퀘스트, 엔드게임, 액션을 확인합니다.

### 8.2 상단 프로필

상단 프로필은 다음 정보를 제공합니다.

- 레벨 배지
- 프로필 제목
- 펫 이름
- 현재 경험치와 다음 레벨 필요 경험치
- 경험치 바

사용자 목적:

- 지금 어느 정도 성장했는지 확인합니다.
- 다음 레벨까지 얼마나 남았는지 봅니다.

규칙:

- 경험치 숫자와 바를 함께 제공합니다.
- 바만 보여주면 정확한 진척을 알기 어렵습니다.
- 숫자만 보여주면 감각적 진행률이 약합니다.

### 8.3 상태 카드

상태 카드는 다음 네 가지를 보여줍니다.

- 기분
- 포만감
- 에너지
- 건강

각 카드는 퍼센트와 하단 미터를 함께 표시합니다.

상태 색상 원칙:

- 좋음: 안정적인 색
- 주의: 경고색
- 나쁨: 위험색

포만감은 배고픔을 직접 보여주는 대신 `100 - hunger`로 표시합니다. 사용자는 "배고픔 80%"보다 "포만감 20%"를 더 직관적으로 위험 상태로 이해할 수 있습니다.

### 8.4 메타 스트립

메타 스트립은 펫의 정체성을 압축해서 보여줍니다.

- 상태
- 단계
- 계열
- 전문성

규칙:

- 각 항목은 라벨과 값으로 구성합니다.
- 긴 값은 줄바꿈 또는 말줄임 처리합니다.
- 이 영역은 조작 대상이 아니라 읽기 전용입니다.

### 8.5 스타일 매트릭스

스타일 매트릭스는 사용자의 개발 행동 성향을 보여줍니다.

표시 항목:

- 기능 출하
- 리팩터링
- 디버깅
- 문서
- 커밋 연속

UX 목적:

- 사용자가 자신의 작업 패턴을 이해합니다.
- 직업 빌드와 연결될 기반을 제공합니다.
- 고레벨 사용자가 부족한 성향을 의식하게 합니다.

규칙:

- 숫자와 상대 막대를 함께 표시합니다.
- 가장 높은 점수를 기준으로 나머지 막대를 비례 표시합니다.
- 이 영역은 경쟁보다 자기 이해에 초점을 둡니다.

## 9. 오늘의 퀘스트 UI

### 9.1 역할

오늘의 퀘스트는 신규 사용자와 반복 사용자를 이어주는 핵심 UI입니다. 사용자는 오늘 무엇을 하면 보상이 생기는지 즉시 알아야 합니다.

### 9.2 퀘스트 미선택 상태

미선택 상태에서는 여러 퀘스트 옵션을 버튼 카드로 보여줍니다.

구성:

- 섹션 제목: 오늘의 퀘스트
- 보조 문구: 오늘 집중할 목표를 하나 고르세요
- 퀘스트 옵션 3개

각 옵션 구성:

- 퀘스트 제목
- 퀘스트 설명

규칙:

- 옵션은 같은 크기의 카드로 보여줍니다.
- 문구는 한눈에 이해되어야 합니다.
- 퀘스트 선택은 하루의 방향을 정하는 행위처럼 느껴져야 합니다.

### 9.3 퀘스트 진행 상태

진행 상태에서는 선택한 퀘스트와 진행률을 보여줍니다.

구성:

- 퀘스트 제목
- 퀘스트 설명
- 진행 바
- 현재 진행 수치
- 보상 문구

예시:

```text
버그 사냥
진단 문제 3개를 해결하세요.
2/3 완료
+90 EXP와 버그 렌즈
```

### 9.4 퀘스트 완료 상태

완료 상태에서는 "오늘 완료"를 명확히 표시합니다. 완료 이후에도 퀘스트 카드는 사라지지 않아야 합니다. 사라지면 사용자는 무엇을 달성했는지 잊습니다.

완료 상태 규칙:

- 상태 문구를 완료로 변경합니다.
- 진행 바는 100%로 유지합니다.
- 보상 문구는 남깁니다.
- 최신 성취 배너와 로그에서도 완료를 확인할 수 있어야 합니다.

## 10. 엔드게임 보드

### 10.1 역할

엔드게임 보드는 고레벨 유저가 계속 돌아오는 이유를 보여주는 핵심 대시보드입니다. 이 영역은 너무 늦게 등장하면 안 됩니다. 퀘스트 바로 아래에 배치해 단기 목표와 장기 목표가 이어지게 합니다.

### 10.2 상단 지표

상단에는 세 가지 지표를 표시합니다.

- 마스터리
- 시즌
- 환생

목적:

- 고레벨 상태를 한눈에 요약합니다.
- 장기 누적 지표를 압축해서 보여줍니다.
- 사용자가 다음 장기 목표를 추측할 수 있게 합니다.

규칙:

- 숫자는 명확해야 합니다.
- 라벨은 짧아야 합니다.
- 시즌 진행률은 현재값과 목표값을 함께 보여줍니다.

### 10.3 직업 빌드 영역

직업 빌드 영역은 사용자의 성장 방향을 선택하거나 확인하는 공간입니다.

직업 미선택 상태:

- 직업 후보 버튼을 표시합니다.
- 각 버튼은 직업 이름을 보여줍니다.
- 향후에는 직업 설명과 보너스를 함께 표시할 수 있습니다.

직업 선택 상태:

- 현재 직업 이름을 강조합니다.
- 직업 설명을 보조 텍스트로 보여줍니다.

UX 원칙:

- 선택은 되돌릴 수 있는지 여부가 명확해야 합니다.
- 되돌릴 수 없다면 확인 절차가 필요합니다.
- 현재 구현처럼 즉시 선택이면 문구에서 부담을 줄여야 합니다.

### 10.4 레이드 보스 영역

레이드 영역은 엔드게임의 가장 강한 시각적 장치입니다.

레이드 미시작 상태:

- 보스를 골라 레이드를 시작하라는 안내
- 격파한 보스 수
- 시작 가능한 보스 버튼 목록

레이드 진행 상태:

- 보스 실루엣
- 보스 이름
- 현재 HP / 최대 HP
- 체력바

UX 원칙:

- 보스가 있다는 사실은 텍스트보다 실루엣으로 먼저 느껴져야 합니다.
- HP는 숫자와 바를 함께 보여줍니다.
- 보스 버튼은 일반 액션 버튼보다 도전 선택처럼 보여야 합니다.

### 10.5 보스 실루엣

보스 실루엣은 픽셀 형태로 표시합니다. Gitagotchi의 픽셀 캐릭터 톤과 맞고, VS Code 안에서도 가볍게 렌더링할 수 있기 때문입니다.

규칙:

- 7x7 픽셀 패턴을 사용합니다.
- 보스마다 다른 패턴을 가집니다.
- 실루엣은 장식이 아니라 상태 인식 장치입니다.
- 애니메이션은 약하게 적용합니다.

### 10.6 주간 회고

주간 회고는 사용자의 작업 성향을 짧은 카드로 보여줍니다.

상태:

- 비어 있음: 다음 활동 후 이번 주 스타일 카드가 생성됩니다.
- 있음: 이번 주 대표 스타일 제목과 요약

UX 목적:

- 사용자가 자신의 개발 패턴을 돌아보게 합니다.
- 통계보다 서사적인 방식으로 회고합니다.
- 향후 공유 카드로 확장할 수 있습니다.

### 10.7 엔드게임 액션

엔드게임 액션은 다음 두 가지입니다.

- 별 조각 제작
- 환생

규칙:

- 조건 미충족 시 비활성화합니다.
- 비활성화된 이유는 향후 툴팁 또는 보조 문구로 제공해야 합니다.
- 환생은 큰 의미의 액션이므로 실수 방지 확인이 필요합니다.

## 11. 액션 독

### 11.1 역할

액션 독은 사용자가 직접 실행할 수 있는 주요 명령을 모아둔 영역입니다.

현재 액션:

- 만져주기
- 커밋 확인
- 통계 보기
- 스킬
- 도감
- 부활

### 11.2 버튼 구조

각 버튼은 룬 코드와 라벨을 함께 표시합니다.

예시:

```text
PT 만져주기
GC 커밋 확인
ST 통계 보기
```

룬 코드는 게임적 감성을 주고, 라벨은 명확성을 보장합니다.

### 11.3 우선순위

가장 중요한 액션은 상태에 따라 primary로 표시합니다.

- 펫이 살아 있음: 만져주기
- 펫이 사망: 부활

나머지 버튼은 보조 액션입니다.

### 11.4 비활성 상태

펫이 사망하면 성장 관련 액션은 비활성화됩니다. 부활은 사망 상태에서만 primary가 됩니다.

규칙:

- 비활성 버튼은 클릭 불가임을 시각적으로 보여줍니다.
- 비활성 상태에서도 라벨은 읽을 수 있어야 합니다.
- 비활성 이유는 향후 툴팁으로 보강합니다.

## 12. 도움말 모달

### 12.1 역할

도움말은 신규 사용자의 이해를 돕지만, 기본 화면을 복잡하게 만들면 안 됩니다. 따라서 모달 방식이 적합합니다.

### 12.2 구성

도움말은 다음 섹션을 포함합니다.

- 성장 방향
- 케어 회복
- 사용 방법
- 매일 만져주기
- 부활

### 12.3 모달 동작

동작 규칙:

- `?` 버튼을 누르면 열립니다.
- 닫기 버튼으로 닫습니다.
- 바깥 영역 클릭 시 닫습니다.
- Escape 키로 닫습니다.

### 12.4 접근성

접근성 규칙:

- `role="dialog"`를 사용합니다.
- `aria-modal="true"`를 사용합니다.
- 제목과 연결되는 `aria-labelledby`를 제공합니다.
- 닫기 버튼에는 명확한 aria-label을 제공합니다.

향후 개선:

- 모달 열림 시 포커스 이동
- 모달 내부 포커스 트랩
- 닫힌 뒤 원래 버튼으로 포커스 복귀

## 13. 상태별 UX

### 13.1 첫 실행 상태

사용자 목표:

- Gitagotchi의 이름을 정합니다.
- 앱이 무엇을 하는지 간단히 이해합니다.

UI 요구사항:

- 이름 입력 흐름이 명확해야 합니다.
- 빈 상태는 무섭거나 고장난 화면처럼 보이면 안 됩니다.
- 오늘의 퀘스트와 펫 카드가 곧 사용 가능하다는 느낌을 줍니다.

### 13.2 정상 성장 상태

사용자 목표:

- 현재 펫 상태를 확인합니다.
- 오늘의 퀘스트를 진행합니다.
- 필요한 액션을 실행합니다.

UI 요구사항:

- 상태 카드와 퀘스트가 명확해야 합니다.
- 성취 배너가 있으면 가장 먼저 보여야 합니다.
- 액션 버튼은 클릭 가능한 상태가 분명해야 합니다.

### 13.3 위험 상태

사용자 목표:

- 펫이 위험하다는 것을 즉시 이해합니다.
- 회복 방법을 찾습니다.

UI 요구사항:

- 건강, 에너지, 포만감의 낮은 상태를 색으로 표시합니다.
- 도움말에서 회복 방법을 확인할 수 있어야 합니다.
- 위험 상태가 지나치게 처벌처럼 느껴지면 안 됩니다.

### 13.4 사망 상태

사용자 목표:

- 펫이 사망 상태임을 이해합니다.
- 부활 가능 여부를 확인합니다.
- 부활 버튼을 실행합니다.

UI 요구사항:

- 성장 관련 액션은 비활성화합니다.
- 부활 버튼을 primary로 표시합니다.
- 부활 조건 부족 시 명확한 메시지를 제공합니다.

### 13.5 퀘스트 미선택 상태

사용자 목표:

- 오늘 집중할 목표를 고릅니다.

UI 요구사항:

- 선택지가 같은 위계로 보여야 합니다.
- 선택 전에 보상 기대를 알 수 있어야 합니다.
- 선택 후 즉시 진행 상태로 바뀌어야 합니다.

### 13.6 퀘스트 완료 상태

사용자 목표:

- 오늘의 목표가 완료됐음을 확인합니다.
- 보상을 이해합니다.

UI 요구사항:

- 완료 문구를 표시합니다.
- 진행률은 100%로 인식되어야 합니다.
- 성취 배너와 로그가 완료를 보강합니다.

### 13.7 레이드 미시작 상태

사용자 목표:

- 시작 가능한 보스를 확인합니다.
- 하나를 선택해 레이드를 시작합니다.

UI 요구사항:

- 보스 선택 버튼은 명확해야 합니다.
- 이미 격파한 보스 수를 보여줍니다.
- 미시작 상태도 빈 공간처럼 보이면 안 됩니다.

### 13.8 레이드 진행 상태

사용자 목표:

- 보스 체력이 얼마나 남았는지 확인합니다.
- 내 활동이 피해로 이어졌는지 확인합니다.

UI 요구사항:

- 보스 실루엣을 표시합니다.
- HP 숫자와 체력바를 함께 표시합니다.
- 타격 이벤트는 순간 배너로 표시합니다.

### 13.9 환생 가능 상태

사용자 목표:

- 환생 가능 여부를 확인합니다.
- 환생의 의미를 이해합니다.

UI 요구사항:

- 환생 버튼이 활성화됩니다.
- 환생 전 확인 절차가 필요합니다.
- 환생 후 별 궤도로 영구 성취를 보여줍니다.

## 14. 사용자 흐름

### 14.1 매일 확인 흐름

1. 사용자가 VS Code를 엽니다.
2. 상태바 또는 명령으로 Gitagotchi 패널을 엽니다.
3. 최신 성취 배너를 확인합니다.
4. 펫 상태와 레벨을 확인합니다.
5. 오늘의 퀘스트를 선택하거나 진행률을 봅니다.
6. 레이드 또는 시즌 진행률을 확인합니다.
7. 필요한 경우 만져주기, 커밋 확인, 통계 보기 등을 실행합니다.

이 흐름은 30초 안에 끝나야 합니다.

### 14.2 성취 확인 흐름

1. 사용자가 개발 행동을 합니다.
2. Gitagotchi가 경험치와 이벤트를 계산합니다.
3. 패널을 열면 최신 성취 배너가 표시됩니다.
4. 관련 영역의 수치가 갱신됩니다.
5. 로그에서 상세 내역을 확인할 수 있습니다.

핵심은 배너와 수치가 같은 이야기를 해야 한다는 점입니다.

### 14.3 레이드 시작 흐름

1. 사용자가 엔드게임 보드로 이동합니다.
2. 레이드 영역에서 시작 가능한 보스를 봅니다.
3. 보스 버튼을 선택합니다.
4. 레이드 영역이 진행 상태로 바뀝니다.
5. 이후 개발 행동이 보스 피해량으로 반영됩니다.

### 14.4 환생 흐름

1. 사용자가 조건을 달성합니다.
2. 환생 버튼이 활성화됩니다.
3. 사용자가 환생을 실행합니다.
4. 확인 절차를 거칩니다.
5. 환생 완료 배너가 표시됩니다.
6. 별 궤도에 새로운 별이 반영됩니다.

## 15. 마이크로인터랙션

### 15.1 버튼 피드백

버튼은 hover, active, disabled 상태를 가져야 합니다.

규칙:

- hover: 경계선 또는 배경이 약하게 강조됩니다.
- active: 눌림 느낌을 줍니다.
- disabled: 클릭 불가가 명확하지만 텍스트는 읽을 수 있어야 합니다.

### 15.2 펫 움직임

펫 스프라이트는 약한 움직임을 가질 수 있습니다. 움직임은 생명감을 주지만 사용자의 코딩 집중을 방해하면 안 됩니다.

규칙:

- 반복 애니메이션은 작고 느리게 적용합니다.
- 큰 흔들림이나 빠른 깜빡임은 피합니다.
- 상태 변화가 있을 때만 강한 반응을 허용합니다.

### 15.3 보스 움직임

보스 실루엣은 약한 펄스를 가집니다. 레이드 중이라는 긴장감을 주되, 화면 전체 주의를 빼앗지 않아야 합니다.

### 15.4 별 궤도

별 궤도는 느리게 회전하거나 배치만으로 표현할 수 있습니다. 별은 환생 성취의 상징이므로 지나치게 빠르게 움직이면 가벼워 보입니다.

### 15.5 배너 등장

성취 배너는 짧게 팝업되는 느낌을 줄 수 있습니다. 다만 레이아웃을 크게 밀어내거나 사용자가 읽기 전에 사라져서는 안 됩니다. 현재 구조처럼 패널 상단에 유지되는 방식이 안정적입니다.

## 16. 비주얼 시스템

### 16.1 전체 톤

전체 톤은 VS Code 테마를 존중하는 어두운 도구형 UI입니다. 색상은 확장 자체가 임의로 지배하기보다 VS Code 변수와 계열별 accent를 조합합니다.

### 16.2 계열별 색상

펫 계열에 따라 accent를 바꿔 카드에 개성을 줍니다.

예시 방향:

- 빌들링: 주황 계열
- 리팩트: 청록 계열
- 디버곤: 붉은 계열
- 아카이복스: 파랑/보라 계열
- 미분기: 연두 계열

색상은 계열성을 보여주되 화면 전체가 한 색으로 잠식되지 않게 해야 합니다.

### 16.3 카드 반경

카드와 버튼은 과하게 둥글면 안 됩니다. VS Code 내부 도구 UI에 맞게 4px에서 8px 사이의 반경을 사용합니다.

### 16.4 타이포그래피

규칙:

- 제목은 짧고 작게 유지합니다.
- 숫자와 수치는 고정폭 폰트 계열을 사용할 수 있습니다.
- 버튼 텍스트는 줄바꿈보다 말줄임을 우선하되, 주요 카드 문구는 줄바꿈을 허용합니다.
- 글자 간격은 과하게 줄이지 않습니다.

### 16.5 아이콘과 룬

현재 액션 버튼은 PT, GC, ST 같은 룬 코드를 사용합니다. 이는 픽셀 RPG 감성을 주는 장치입니다. 다만 룬만으로는 의미가 부족하므로 라벨과 항상 함께 표시해야 합니다.

향후 아이콘을 추가한다면 VS Code 스타일과 충돌하지 않는 단색 아이콘을 사용합니다.

## 17. 문구 전략

### 17.1 원칙

Gitagotchi의 문구는 다음 원칙을 따릅니다.

- 짧게 말합니다.
- 결과를 명확히 말합니다.
- 과장된 칭찬을 피합니다.
- 사용자의 실제 개발 행동과 연결합니다.
- 실패를 비난하지 않습니다.

### 17.2 좋은 문구 예시

- 오늘의 집중 목표를 완료했습니다.
- 작업이 보스에게 피해를 줬습니다.
- 다음 활동 후 이번 주 스타일 카드가 생성됩니다.
- 보스를 골라 레이드를 시작하세요.
- Gitagotchi가 별을 품고 다음 생으로 넘어갑니다.

### 17.3 피해야 할 문구

- 지금 당장 더 하세요.
- 실패했습니다.
- 당신은 게을렀습니다.
- 엄청난 전설이 시작됐습니다.
- 최고의 개발자입니다.

Gitagotchi는 사용자를 압박하는 생산성 도구가 아니라, 개발 루틴을 부드럽게 게임화하는 도구입니다.

## 18. 접근성 상세 기준

### 18.1 키보드 접근성

모든 주요 버튼은 키보드로 접근 가능해야 합니다.

대상:

- 언어 버튼
- 이름 변경
- 초기화
- 도움말
- 퀘스트 선택
- 직업 선택
- 레이드 시작
- 엔드게임 액션
- 액션 독 버튼

### 18.2 포커스 표시

포커스 상태는 명확해야 합니다. VS Code의 `focusBorder`를 활용해 키보드 사용자가 현재 위치를 알 수 있게 해야 합니다.

### 18.3 색상 의존성

상태는 색상만으로 전달하면 안 됩니다.

예:

- 건강 20%는 붉은색뿐 아니라 숫자 `20%`가 있어야 합니다.
- 레이드 HP는 체력바뿐 아니라 `HP 120/260`이 있어야 합니다.
- 완료 상태는 색상뿐 아니라 `오늘 완료` 문구가 있어야 합니다.

### 18.4 애니메이션

애니메이션은 의미 전달의 필수 요소가 아니어야 합니다. 사용자가 애니메이션을 보지 못해도 성취, 상태, 진행률을 이해할 수 있어야 합니다.

향후 개선:

- `prefers-reduced-motion` 대응
- 강한 애니메이션 비활성화 옵션

### 18.5 스크린 리더

현재 스프라이트, 하트, 별, 체력바에는 aria-label이 필요합니다. 장식적 요소는 `aria-hidden`을 사용할 수 있고, 의미가 있는 요소는 텍스트 대체를 제공해야 합니다.

## 19. 반응형 기준

### 19.1 넓은 화면

넓은 화면에서는 두 열 구조를 사용합니다.

- 펫 카드 폭은 안정적으로 유지합니다.
- 시스템 카드는 남은 공간을 사용합니다.
- 퀘스트 옵션은 3열로 표시합니다.
- 엔드게임 보드는 2열 구조를 유지합니다.

### 19.2 중간 화면

중간 화면에서는 일부 그리드를 2열로 줄입니다.

- 상태 카드는 2열
- 스타일 매트릭스는 2열 또는 자동 줄바꿈
- 퀘스트 옵션은 2열

### 19.3 좁은 화면

좁은 화면에서는 단일 열 중심으로 전환합니다.

주의:

- 액션 독 버튼이 너무 좁아지면 라벨이 잘릴 수 있습니다.
- 버튼의 최소 높이는 유지합니다.
- 퀘스트 카드는 세로로 쌓는 편이 낫습니다.

## 20. 빈 상태와 오류 상태

### 20.1 활동 없음

활동이 없을 때는 "아직 활동이 없습니다."처럼 차분한 문구를 사용합니다. 빈 상태는 사용자를 비난하지 않아야 합니다.

### 20.2 퀘스트 없음

퀘스트 선택지가 없는 상황은 가능하면 발생하지 않아야 합니다. 만약 발생한다면 "오늘 선택 가능한 퀘스트를 준비 중입니다."처럼 안정적인 문구를 사용합니다.

### 20.3 레이드 없음

레이드가 시작되지 않은 상태는 빈 상태가 아니라 선택 대기 상태입니다.

권장 문구:

- 보스를 골라 레이드를 시작하세요.
- 격파한 보스 0마리

### 20.4 주간 회고 없음

권장 문구:

- 다음 활동 후 이번 주 스타일 카드가 생성됩니다.

이 문구는 사용자가 다음에 무엇을 하면 상태가 바뀌는지 알려줍니다.

## 21. 현지화 UX

### 21.1 언어별 길이 차이

한국어, 영어, 일본어, 중국어는 문장 길이와 줄바꿈 특성이 다릅니다. UI는 긴 영어 문구와 짧은 중국어 문구 모두에서 깨지지 않아야 합니다.

규칙:

- 버튼 라벨은 짧게 유지합니다.
- 카드 설명은 줄바꿈을 허용합니다.
- 고정 폭이 필요한 영역에는 말줄임 처리를 적용합니다.
- 보상 문구는 숫자와 보상명을 분리해 읽기 쉽게 유지합니다.

### 21.2 문화적 톤

모든 언어에서 과도한 격려나 압박을 피합니다. Gitagotchi의 톤은 친근하지만 업무 도구에 맞게 절제되어야 합니다.

- 디버그 로그나 임시 안내 문구가 남아 있지 않습니다.

## 26. 최종 UX 판단

이번 UI/UX의 핵심은 화면을 화려하게 만드는 것이 아닙니다. 사용자가 Gitagotchi를 열었을 때 "내 개발 행동이 하나의 성장 세계 안에서 계속 이어지고 있다"는 감각을 주는 것입니다.

따라서 좋은 UI는 다음 조건을 만족해야 합니다.

- 펫은 정서적 중심입니다.
- 퀘스트는 오늘의 행동 이유입니다.
- 레이드는 고레벨 사용자의 공략 대상입니다.
- 시즌과 마스터리는 장기 진행도입니다.
